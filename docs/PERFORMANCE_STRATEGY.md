# Performance Strategy

The side panel paints a lightweight loading shell immediately, reads the current page and cached note locally, and never waits for BYOS before enabling editing. The Gutenberg editor remounts only when the page key changes.

Autosave debounces changes for 750 ms, hashes normalized content, skips unchanged metadata/content, and coalesces remote work by page key. Storage indexes avoid scanning unrelated origins for the root-page list, while a revision gate coalesces local change-event bursts and suppresses intermediate or stale list results. Migration and full synchronization may use bounded batches with event-loop yielding.

Remote listing and reconciliation run in the background on explicit opportunities rather than polling continuously. Retry uses bounded exponential backoff and alarms so worker suspension does not create tight loops. Temporary credentials are reused only until their early-adjusted expiry.

Production hardening measures emitted package size, editor-load latency, local note-load latency, large-document save time, full-origin index time, and large-replica reconciliation. Initial performance budgets are a production JavaScript package under 5 MiB compressed, cached note shell feedback under 100 ms on a typical desktop profile, and no long task over 200 ms outside initial editor loading; measured exceptions must be recorded before release. The `0.1.7` deterministic package contains 4,446,241 raw JavaScript bytes and 1,148,594 gzip-compressed JavaScript bytes, including a 3,987,098-byte side-panel entry, 220,873-byte service worker, 145,165-byte shared React/runtime entry, 75,882-byte sync-queue shared entry, and 17,223-byte options entry, so the compressed JavaScript package remains within budget while the initial editor chunk remains an explicit loading-performance target. The dependency-free stored release ZIP is 5,071,184 bytes, 171,696 bytes below 5 MiB; this margin is acceptable for the release artifact but must be watched when the editor graph changes.

The prospective `0.1.9` memory work uses the published `0.1.8` build as its attribution baseline: the side-panel JavaScript entry is 3,987,452 bytes and its stylesheet is 422,187 bytes. In a controlled headless Chromium profile, opening the panel on an unsupported page used 9.3 MiB of JavaScript heap from a 13.9 MiB heap, while mounting a supported-page editor used 12.7 MiB from a 21.2 MiB heap. The likely panel renderer grew from approximately 155 MiB to 170.9 MiB and the complete Chromium process tree grew by approximately 29.3 MiB; RSS is directional because native and shared Chromium allocations cannot be attributed perfectly. PP-027 through PP-029 must record like-for-like production artifact sizes after each local commit and repeat the controlled runtime probe where technically stable. These optimizations must not trade away editor semantics, local-first reliability, or safe paste behavior.

PP-027 removes the complete registry entries and emits exactly eight block modules and nine format modules. The accepted production `side-panel.js` is 3,253,410 bytes, 734,042 bytes or 18.4% below the `0.1.8` baseline; `side-panel.css` remains 422,187 bytes. A like-for-like non-forced-GC CDP probe measured 9.32 MiB used heap from a 12.60 MiB heap on the unsupported panel and 12.68 MiB from a 16.60 MiB heap after mounting the supported editor, a 3.36 MiB used-heap delta. An additional forced-GC probe measured 7.59 MiB before mount and 9.64 MiB after, a 2.05 MiB delta. The mounted used-heap result is effectively unchanged from baseline, so PP-027 is an 18.4% code-graph/package win rather than a claimed mounted-heap win; PP-028 owns avoiding this graph entirely on unsupported pages.

PP-028 reduces the eager production side-panel shell to 42,683 bytes and moves 3,211,143 bytes of editor JavaScript plus 422,187 bytes of editor CSS behind the supported-page boundary. A fail-closed production audit verifies exact lazy assets, stable shell references, absent eager HTML resource references, editor markers only in the lazy chunk, and a 96-KiB shell budget; packaged Chromium request evidence proves an unsupported panel fetches neither editor resource and a supported navigation fetches both before real typing. A like-for-like non-forced-GC CDP probe measured 2.67 MiB used heap from a 3.80 MiB heap on the unsupported panel and 12.92 MiB from a 16.35 MiB heap after mounting the editor. The unsupported used-heap result is 6.65 MiB or approximately 71% below PP-027, while supported heap remains effectively unchanged as expected; PP-029 therefore targets transfer and style-processing cost rather than promising another unsupported-state heap change.

PP-029 replaces the complete isolated-editor CSS bundle with exact ordered imports for the Gutenberg component and editor framework, format and edit-post structure, common editor elements, and only the style families belonging to PagePerch's eight registered text blocks. The production `PageNoteEditor.css` is 246,609 bytes, 175,578 bytes or 41.6% below PP-028 and the `0.1.8` baseline, while the 42,683-byte shell and 3,211,143-byte lazy editor JavaScript remain unchanged. Exact-import, marker, unsupported-block, and maximum-size audits protect the composition without coupling tests to declaration values; all eight browser behaviors protect rendered editing. A final non-forced-GC CDP probe measured 2.63 MiB used heap from a 3.55 MiB heap on the unsupported panel and 12.90 MiB from a 16.85 MiB heap after editor mount, confirming that the CSS-only change does not materially alter JavaScript heap.
